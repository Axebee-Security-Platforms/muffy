# Setup

Steps 1-4 are the **common setup**: every lane runs them first, the fix and change lanes too. Those lanes then follow their own setup-lite ([fix-profile.md](fix-profile.md), [change-profile.md](change-profile.md)) instead of steps 5-8. Values steps 1-4 produce (`baseline`) are held and written into `## Status` when the lane writes its checkpoint.

1. `<brain>` = `<vault>/Projects/<repo-name>/`, or `.team/brain/` when there is no vault; create `project.md`, `tasks/`, `agents/<role>/` (one per agent) if missing. The task's `.team/` folders come at step 7, inside the feature worktree
2. Create `<brain>/tasks/<task>.md` (frontmatter `project`, `task`, `date`, `status` + `[[agents/<role>/<task>]]` links); add the task to `project.md` → `## Tasks` as `in progress`
3. **Baseline check**: `node .claude/skills/muffy/scripts/next-action.mjs baseline --lane <lane>` (add `--no-code` when the repo has no source files: `scan-repo.mjs` → `hasCode` false). It reads `check-baseline.mjs --json` and the depth the lane needs (`lanes.mjs`: fix and an internal change need a quick baseline, a visible change and the full flow a full one; give the change lane `--scope`), then prints one `next=`:
   - `continue`: hold `baseline: green` (nothing to hold with `--no-code`). Pass `docs/architecture/baseline.md` to researcher and architect, read nothing more
   - `refresh:silent`: the baseline is yellow. Run onboard's refresh ([onboard.md](onboard.md#refresh)) without asking, tell the user one line (`baseline: refreshed (<n> files changed)`), hold `baseline: green`, carry on. No question
   - `ask:onboard-quick` or `ask:onboard-full`: no usable baseline. One `AskUserQuestion`: "ยังไม่รู้จักโปรเจกต์นี้ ขอสำรวจก่อนแล้วทำงานนี้ต่อเลยไหม / I don't know this project yet: look around first, then carry on with this?" with **look first (recommended)** / **skip for now**. Look first: write `.team/onboard/pending-request.md` (the request verbatim and the route picked) and run onboard at that depth ([onboard.md](onboard.md#depth)); its last step comes back here with the request. Skip: hold `onboard skipped by the user` (no `baseline:` item) and carry on with the code as the only truth
   - `ask:red`: read [baseline-freshness.md](baseline-freshness.md) and ask as it says (the question goes in the second `pause:scope` call, step 5)
4. Read `project.md` (Lessons, Open issues, backlog). Resuming: follow [resume.md](resume.md) instead
5. **Confirm scope** (`pause:scope`): state the feature slice in one or two lines and the explicit out-of-scope list. Multi-feature requests are cut to one slice here, never inside a step. Ask with `AskUserQuestion`, which takes at most 4 questions per call and 2-4 options per question. Call 1, one question each, skipping any that `project.md` or `deploy.md` already answers:
   - **Plan**: the card from `next-action.mjs plan-card feature`, go / stop earlier / smaller ([route.md](route.md#say-the-plan))
   - **Scope**: confirm the slice (Confirm / Change it)
   - **Base branch** (only when `main` and the current branch differ): the current branch / `main`. Record it as `base: <branch>` in checkpoint `## Status`

   Call 2, only if needed: **Release announcement** (user-facing feature only; off by default; the answer is a suggestion for the user to accept, so yes → `announcement: yes` in the docs-writer prompt and benefit-focused text in release-notes.md); the **baseline** question from step 3 when it is red (yellow is refreshed without a question), worded as [baseline-freshness.md](baseline-freshness.md) says; and the **commit trailer** only when the harness gives no attribution line (SKILL.md rules).
6. **Pick the run profile** ([run-profile.md](run-profile.md)), state it to the user in one line, and create the todo list from the steps it keeps. Its lane line is written in step 8 with `node .claude/skills/muffy/scripts/checkpoint.mjs profile .team/<task> feature [--skip <steps>]`
7. **Worktrees and the team folder** (`<role>` = the short prefix: `ops`, `fe`, `be`, `qa`). `<base>` comes from step 5 and is **not assumed to be `main`**. The feature worktree is the task's home from setup on: create it now, then `.team/<task>/`, `handoff/` and `rounds/` inside it. Tell each agent that this copy of `.team/<task>/` is the authoritative one:
   `git worktree add .worktrees/feature-<task> -b feature/<task> <base>`

   A worktree sees only committed files, so the planning files (`ac.md`, `brief.md`, `contract.md`, `design.md`, `deploy.md`, any migration numbers the contract reserves) are committed to `feature/<task>`, never to `<base>`, once the design gate passes (step 3c), or before 3d or step 4 when 3c is skipped. Check with `git status --short .team/` first. A later planning change is committed the same way, then merged into each branch that already exists (`git -C <worktree> merge feature/<task>`) before its agent continues.

   A baseline committed at step 3 (a quick onboard or a silent refresh, `baseline-commit: <sha>`) on a branch other than `<base>`: `git -C .worktrees/feature-<task> cherry-pick <sha>` right after this worktree is cut ([onboard.md](onboard.md#commit-without-0d)).

   Cut the other worktrees from that commit, never from `<base>`: ops at step 3d, if the profile keeps it: `git worktree add .worktrees/ops-<task> -b ops/<task> feature/<task>`. After 3d passes, fe and be from it: `git worktree add .worktrees/<role>-<task> -b <role>/<task> ops/<task>`. If 3d is skipped, cut them from `feature/<task>`. qa is created at step 7 from the reviewed branch. Agents receive the paths; they never create worktrees on the fly

   **Sync the skill into every worktree you create**, right after its `git worktree add`: `node .claude/skills/muffy/scripts/sync-worktree.mjs .worktrees/<role>-<task>`. A worktree carries the copy of `.claude/skills/muffy/` that was committed when it was cut, so a script staged in the main checkout since (a newer `validate-handoff.mjs`, `checkpoint.mjs`) would be stale there and subagents would reject valid hand-offs. Commit what it copies as the worktree's first commit (`chore(muffy): sync skill scripts`). `--check` lists the differences without copying (exit 1 if any); run it before spawning into a worktree that already existed
8. Write the first `.team/<task>/checkpoint.md` in the feature worktree ([memory-model.md](memory-model.md#checkpoint)): pin `## Goal` verbatim from the request, then the run profile (lane line by `checkpoint.mjs profile`, step 6), and the scope confirmed in step 5. Values held from steps 3 and 5 (`baseline`, `base`, `announcement`) are written into `## Status` here, since the folder and checkpoint do not exist before this step
