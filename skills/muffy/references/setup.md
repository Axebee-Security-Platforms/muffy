# Setup

Small bug or cosmetic fix (`/muffy fix`, or it passes the triage in [fix-profile.md](fix-profile.md)): follow the setup-lite in `fix-profile.md` instead of the steps. Internal work that passes the triage in [lite-profile.md](lite-profile.md) (`/muffy lite`) follows that file's setup-lite instead below.

1. `<brain>` = `<vault>/Projects/<repo-name>/`, or `.team/brain/` when there is no vault; create `project.md`, `tasks/`, `agents/<role>/` (one per agent) if missing. The task's `.team/` folders come at step 7, inside the feature worktree
2. Create `<brain>/tasks/<task>.md` (frontmatter `project`, `task`, `date`, `status` + `[[agents/<role>/<task>]]` links); add the task to `project.md` → `## Tasks` as `in progress`
3. **Baseline check** (existing codebase only; `scan-repo.mjs` → `hasCode`): read `docs/architecture/baseline.md` first and pass its path to researcher and architect. Then run `node .claude/skills/muffy/scripts/check-baseline.mjs` once and record `baseline: green|yellow|red` in checkpoint `## Status`: green → carry on and read nothing more; yellow or red → read [baseline-freshness.md](baseline-freshness.md) and ask as it says (the question goes in the second `pause:scope` call, step 5). Missing → `AskUserQuestion`: run `/muffy onboard` first (recommended) or continue without it, recorded in checkpoint. Frontmatter `commit` more than 100 commits behind HEAD → suggest a refresh. See [onboard.md](onboard.md)
4. Read `project.md` (Lessons, Open issues, backlog). Resuming: follow [resume.md](resume.md) instead
5. **Confirm scope** (`pause:scope`): state the feature slice in one or two lines and the explicit out-of-scope list. Multi-feature requests are cut to one slice here, never inside a step. Ask with `AskUserQuestion`, which takes at most 4 questions per call and 2–4 options per question. Call 1, one question each, skipping any that `project.md` or `deploy.md` already answers:
   - **Scope**: confirm the slice (Confirm / Change it)
   - **Base branch** (only when `main` and the current branch differ): the current branch / `main`. Record it as `base: <branch>` in checkpoint `## Status`
   - **Staging**: yes / substitute (say which environment) / none. Save as `staging: <yes | substitute: …| none>` in checkpoint `## Status` and `project.md`; devops reads it, never guesses from its survey
   - **Infrastructure** (skip in the fix lane): existing (say what) / none yet, decide later (the default) / none yet, propose one now / not needed (a library, local tool or client-only app). Record as `infra: <existing: …| later | propose | not-needed>` in checkpoint `## Status` and `project.md`. "None" is a normal answer, never an error; nothing is proposed unless the user chose `propose`. See [infrastructure-options.md](../../../agents/references/devops/infrastructure-options.md)

   Call 2, only if needed: **Release announcement** (user-facing feature only; off by default; the answer is a suggestion for the user to accept, so yes → `announcement: yes` in the docs-writer prompt and benefit-focused text in release-notes.md); the **baseline** question from step 3 when it is yellow or red, worded as [baseline-freshness.md](baseline-freshness.md) says; and the **commit trailer** only when the harness gives no attribution line (SKILL.md rules).

   When a question is skipped because `project.md` records the answer, still copy that `infra:` line into this task's checkpoint `## Status` (`check-artifacts.mjs` reads it there).
6. **Pick the run profile** ([run-profile.md](run-profile.md)), state it to the user in one line, and create the todo list from the steps it keeps
7. **Worktrees and the team folder** (`<role>` = the short prefix: `ops`, `fe`, `be`, `qa`). `<base>` comes from step 5 and is **not assumed to be `main`**. The feature worktree is the task's home from setup on: create it now, then `.team/<task>/`, `handoff/` and `rounds/` inside it. Tell each agent that this copy of `.team/<task>/` is the authoritative one:
   `git worktree add .worktrees/feature-<task> -b feature/<task> <base>`

   A worktree sees only committed files, so the planning files (`ac.md`, `brief.md`, `contract.md`, `design.md`, `deploy.md`, any migration numbers the contract reserves) are committed to `feature/<task>`, never to `<base>`, once the design gate passes (step 3c), or before 3d or step 4 when 3c is skipped. Check with `git status --short .team/` first. A later planning change is committed the same way, then merged into each branch that already exists (`git -C <worktree> merge feature/<task>`) before its agent continues.

   Cut the other worktrees from that commit, never from `<base>`: ops at step 3d, if the profile keeps it: `git worktree add .worktrees/ops-<task> -b ops/<task> feature/<task>`. After 3d passes, fe and be from it: `git worktree add .worktrees/<role>-<task> -b <role>/<task> ops/<task>`. If 3d is skipped, cut them from `feature/<task>`. qa is created at step 7 from the reviewed branch. Agents receive the paths; they never create worktrees on the fly
8. Write the first `.team/<task>/checkpoint.md` in the feature worktree ([memory-model.md](memory-model.md#checkpoint)): pin `## Goal` verbatim from the request, then the run profile, and the scope confirmed in step 5. Values held from steps 3 and 5 (`baseline`, `base`, `staging`, `infra`, `announcement`) are written into `## Status` here, since the folder and checkpoint do not exist before this step
