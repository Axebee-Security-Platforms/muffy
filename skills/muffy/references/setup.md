# Setup

Small bug or cosmetic fix (`/muffy fix`, or it passes the triage in [fix-profile.md](fix-profile.md)): follow the setup-lite in `fix-profile.md` instead of the steps below.

1. Create `.team/<task>/`, `.team/<task>/handoff/` and `.team/<task>/rounds/`. `<brain>` = `<vault>/Projects/<repo-name>/`, or `.team/brain/` when there is no vault; create `project.md`, `tasks/`, `agents/<role>/` (one per agent) if missing
2. Create `<brain>/tasks/<task>.md` (frontmatter `project`, `task`, `date`, `status` + `[[agents/<role>/<task>]]` links); add the task to `project.md` → `## Tasks` as `in progress`
3. **Baseline check** (existing codebase only; `scan-repo.mjs` → `hasCode`): read `docs/architecture/baseline.md` first and pass its path to researcher and architect. Missing → `AskUserQuestion`: run `/muffy onboard` first (recommended) or continue without it, recorded in checkpoint. Frontmatter `commit` more than 100 commits behind HEAD → suggest a refresh. See [onboard.md](onboard.md)
4. Read `project.md` (Lessons, Open issues, backlog). Resuming: follow [resume.md](resume.md) instead
5. **Confirm scope** (`pause:scope`): state the feature slice in one or two lines and the explicit out-of-scope list; `AskUserQuestion` until the user confirms. Multi-feature requests are cut to one slice here, never inside a step. If the feature is user-facing, add one line to the same question: "Release announcement: off. Want one? (benefit-focused text in release-notes.md)"; the answer is a suggestion for the user to accept, never assumed. Yes → put `announcement: yes` in the docs-writer prompt. Add one more line to the same question (skip if `project.md` or `deploy.md` already records the answer): "Staging: is there one, or which environment stands in for it?" Save the answer as `staging: <yes | substitute: …| none>` in checkpoint `## Status` and `project.md`; devops reads it, never guesses from its survey
6. **Pick the run profile** ([run-profile.md](run-profile.md)), state it to the user in one line, and create the todo list from the steps it keeps
7. **Worktrees** (`<role>` = the short prefix: `ops`, `fe`, `be`, `qa`). `<base>` is the branch the feature will merge into, **not assumed to be `main`**: ask in the `pause:scope` question when `main` and the current branch differ, and record it in checkpoint `## Status` as `base: <branch>`. A worktree sees only committed files, so before creating any worktree commit the planning files (`.team/<task>/` ac, contract, design, brief, and any new migration numbers the contract reserves) to `<base>` or to a feature branch cut from it, and verify with `git status --short .team/`. A worktree cut from a stale `main` would show the agent old code and no plan. At setup create only the ops worktree, if the profile keeps step 3d: `git worktree add .worktrees/ops-<task> -b ops/<task> <base>`. After 3d passes, before step 4, create `fe` and `be` from the smoke-tested base: `git worktree add .worktrees/<role>-<task> -b <role>/<task> ops/<task>`. If 3d is skipped, create them from `<base>` instead. Tell each agent which copy of `.team/<task>/` is authoritative (the worktree's own, after the commit above). qa is created at step 7 from the reviewed branch. Agents receive the paths; they never create worktrees on the fly
8. Write the first `.team/<task>/checkpoint.md` ([memory-model.md](memory-model.md#checkpoint)): pin `## Goal` verbatim from the request, then the run profile, and the scope confirmed in step 5
