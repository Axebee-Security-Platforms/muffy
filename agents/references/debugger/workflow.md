## Workflow

1. Read `fix.md` and only the files it names. Reproduce first: run the failing test or command, or write one that fails (kept out of the source tree, or as a temporary file you delete). If you cannot reproduce, say so; do not guess
2. Make the repro tight before theorising: one command you have already run, that goes red on this symptom (not merely "runs"), gives the same verdict every run and finishes in seconds. A flaky bug: loop the trigger until the failure rate is high enough to debug against. Then shrink it: cut inputs, config and steps one at a time, re-running after each cut, and keep only what still fails
3. Trace the failing path from symptom to cause. List 2 or 3 hypotheses, each falsifiable ("if X is the cause, changing Y makes it vanish"), then test them one at a time against a second piece of evidence (a second input, a log line, a `git log -p` of the file), changing one variable per probe. One that does not hold is dropped, not patched. Temporary debug logs are allowed in the worktree only: tag each `[DEBUG-<4 hex>]` and remove them all (`grep` the tag) before hand-off; `git diff` on source must be empty
4. Rate the severity from the impact of the bug (scale in Rules and Guardrails), then check you hold the minimum evidence for that tier. If you do not, get it or lower the confidence and say what is missing
5. Decide the owner: `FE`, `BE` or `both`, from where the cause lives (`files` per owner in `## Cause`)
6. Write `## Cause` (one line + confidence + severity + owner), `## Repro` and `## Evidence` (the probes you ran and what each showed, including the hypotheses you dropped) in `fix.md`. Change nothing else in it
7. Flow diagram, only if needed: when you cannot find the cause without first understanding a flow that spans three or more participants (client, API, DB, queue, third party) or whose ordering is not obvious, write `.team/<task>/flow.html`: one `kind: flow` diagram of that flow as the code runs it, copied from the template and styled per [diagram-style.md](../shared/diagram-style.md) (at most 12 steps, every step labelled, `fail: true` on the failing step), then run `node .claude/skills/muffy/scripts/check-diagram.mjs` and `check-diagram-render.mjs` on it and fix a layout FAIL before hand-off. Draw it from the code you traced, never from memory; mark anything unconfirmed `verify: true`. Link it from `## Cause` and list it in `paths_written`. None when the cause is already clear
8. Hand off: `known`, `unknown` or `needs-full-flow` (cause is in the contract, a dependency, the stack or a design decision; do not work around it)
9. Record in `<brain>/agents/debugger/<task>.md`: date, cause, severity, hypotheses dropped, open issues (≤ 5 lines)
